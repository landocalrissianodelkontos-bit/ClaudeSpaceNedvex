# Парсер судебных дел (юр. отдел)

Читает таблицу дел (xlsx), определяет тип сайта суда по ссылке, скачивает
актуальные данные по каждому делу с сайта суда и собирает сводный
Excel-отчёт для анализа.

## Что уже проверено на реальных данных

На вашей выгрузке (`Перечень_всех_объектов_и_вопросов_юр_отдела_-_Девелопмент.xlsx`,
157 строк, 2 листа) обнаружено **4 типа ссылок**, не 2-3:

| Тип (`court_type`)             | Домен                | Кол-во | Как парсим |
|---------------------------------|-----------------------|-------:|------------|
| `arbitrazh_kad`                 | kad.arbitr.ru          | 71     | Playwright (браузер, SPA) |
| `general_jurisdiction_sudrf`    | *.sudrf.ru             | 69     | requests + BeautifulSoup (обычный HTML) |
| `moscow_city`                   | mos-gorsud.ru          | 5      | Playwright (браузер, SPA) |
| `magistrate_msudrf`             | *.msudrf.ru (мировые судьи) | 3 | requests + BeautifulSoup, тот же движок, что sudrf.ru |
| `empty` / без ссылки            | —                       | 9      | не парсится, дела до ~2011 г. без ссылки в системе — только вручную |

Это уже учтено в коде (`config.COURT_TYPE_PATTERNS`, `scraper_runner.py`).
Если пришлёте таблицу с другими доменами судов — добавьте паттерн в
`config.py`, отдельный скрапер не всегда нужен: если верстка похожа на
sudrf.ru — переиспользуйте `scrapers/sudrf.py`, если это SPA — берите за
основу `scrapers/kad_arbitr.py` или `scrapers/mos_gorsud.py`.

Исходный файл был с повреждённым `stylesheet.xml` (обычное дело после
некоторых экспортов) — `excel_io.py` умеет такое автоматически чинить через
LibreOffice, если `soffice` есть в PATH, а если LibreOffice недоступен
(или сам падает, как в песочнице Claude Code) — прямой правкой XML в
styles.xml (см. следующий раздел).

## Что реально проверено на живых сайтах (в песочнице Claude Code)

- **excel_io.py**: ваш файл не открывался не из-за "битого stylesheet.xml"
  вообще, а из-за конкретного невалидного значения
  `horizontal="-webkit-center"` в `xl/styles.xml` (явно осталось от
  экспорта через HTML→xlsx конвертер — валидный OOXML enum такого значения
  не знает). В этой песочнице LibreOffice (`soffice`) вообще не запускается
  (падает даже на тривиальном файле), поэтому добавлен второй, независимый
  от LibreOffice способ починки — прямая правка XML внутри styles.xml.
  Если у вас `soffice` работает нормально — он по-прежнему пробуется первым.
- **scrapers/sudrf.py** — проверено на живых страницах нескольких регионов
  (Вологодская область, Санкт-Петербург, Свердловская область, Краснодарский
  край) и переписано по итогам:
  - таблица "Движение дела" на самом деле имеет вид `<td>Название события</td>
    <td>дд.мм.гггг</td>` (дата — во ВТОРОЙ ячейке), а не наоборот, как было в
    первой версии — из-за этого движение по делу раньше не собиралось вообще;
  - номер дела в привычном формате ("2-3772/2024") берётся из заголовка
    `div.casenumber`, а не из таблицы (там только служебный УИД дела);
  - добавлено вычисление `next_hearing_date` (ближайшая ещё не наступившая
    дата из движения по делу) и `instance` (из заголовка раздела);
  - **важное наблюдение, не связанное с версткой**: суды Краснодарского края
    (`*--krd.sudrf.ru` — 57 из 71 строки с этим типом ссылки в вашей таблице)
    отдают "Информация временно недоступна" даже на странице поиска —
    похоже, модуль "Судебное делопроизводство" там отключён на уровне сайта.
    Это не чинится селекторами; скрапер теперь возвращает по этим делам
    понятную ошибку вместо "проверьте вёрстку". Суды других регионов (СПб,
    Вологда, Свердловская обл.) отдают данные нормально.
  - также добавлено распознавание капчи (`*.msudrf.ru` иногда её показывает).
- **scrapers/kad_arbitr.py** — реальный экран капчи не содержит слова
  "captcha" в видимом тексте (там "Подтверждение действия" / "Введите код с
  картинки" / "Превышено количество попыток ввода кода") — прежняя проверка
  его не ловила и отчитывалась как "верстка изменилась". Поправлено.
- **scrapers/mos_gorsud.py** и **kad_arbitr.py**: `page.goto(..., 
  wait_until="networkidle")` заменено на `"domcontentloaded"` — на этих
  страницах есть фоновые long-polling запросы, из-за которых сеть никогда
  не "затихает".

## Известное ограничение среды: Playwright/Chromium в этой песочнице

В песочнице, где это писалось, у Chromium (через Playwright) полностью не
проходит TLS-хендшейк на HTTPS **вообще для любого сайта**, включая
`https://example.com` — соединение обрывается (`net::ERR_CONNECTION_RESET`)
ещё на уровне ClientHello, судя по netlog. Это подтверждено: `curl` и
`requests` из той же песочницы к тем же сайтам подключаются нормально, то
есть дело не в блокировке kad.arbitr.ru/mos-gorsud.ru конкретно, а в
сетевой политике самой песочницы для процесса Chromium. Добавлена попытка
явно передать прокси браузеру (`scrapers/base.py:playwright_launch_kwargs`,
из `HTTPS_PROXY`/`https_proxy`) — она не помогла именно в этой песочнице, но
может помочь в вашем окружении, если там прокси настроен иначе, поэтому
оставлена.

**Из-за этого `kad_arbitr.py` и `mos_gorsud.py` не удалось до конца
проверить на живых страницах в этой сессии** — их всё равно стоит
прогнать смок-тестом (`scrape --limit 2 --court-types
arbitrazh_kad,moscow_city`) у себя, там, где Chromium может нормально
открывать HTTPS. Дополнительно: `mos-gorsud.ru` в этой песочнице (через
`curl`/`requests`, не Playwright) отвечал крайне медленно и рвался по
таймауту даже за 90 секунд, хотя часть реальных данных (таблицу "Судебные
заседания и беседы") успевал прислать — это тоже похоже на защиту от
автоматических обращений (trottling/tarpit), а не на проблему кода; при
живом прогоне возможно потребуется завышенный `REQUEST_TIMEOUT` и
увеличенные задержки между запросами (см. `config.py`).

**Первым делом при запуске у вас (там уже есть интернет) нужно:**

```bash
pip install -r requirements.txt
playwright install chromium

# 1. Быстрая проверка классификации — сеть не нужна
python main.py --input input.xlsx classify --show-unknown

# 2. Смок-тест: по 2 дела с каждого типа сайта
python main.py --input input.xlsx scrape --limit 2
```

Затем откройте `data/raw/<court_type>/*.json` — там сохранён сырой HTML,
который реально пришёл с сайта — и `data/output/scraped_merged.xlsx` со
структурированным результатом. Если для kad.arbitr.ru / mos-gorsud.ru
поля пустые (`scraped_error` заполнен) — откройте 2-3 реальные ссылки в
браузере, посмотрите DOM (F12) и поправьте `SELECTORS` в соответствующем
файле `scrapers/*.py`. Заготовки под это есть в докстрингах каждого файла.

## Запуск полного цикла

```bash
# Скрапинг всех дел (использует кэш — повторный запуск не дёргает сайты заново)
python main.py --input input.xlsx scrape

# Отчёт по накопленным данным
python main.py --input input.xlsx analyze --merged data/output/scraped_merged.xlsx \
    --output data/output/report.xlsx

# либо всё за один прогон
python main.py --input input.xlsx all
```

Отчёт (`report.xlsx`) содержит:
- **Все дела** — исходная таблица + всё, что удалось спарсить с сайта суда
  (актуальный статус, судья, стороны, движение по делу, дата следующего
  заседания, документы) рядом с тем, что было вручную вписано в таблицу —
  так виден расхождения ("в таблице написано «в процессе», а на сайте суда
  уже есть решение").
- **by_court_type / by_result / by_instance / by_party_role** — сводки по
  исходной таблице (данные нормализуются: опечатки и варианты формулировок
  типа "Апелляция"/"Апелляционная инстанция"/"Апклляционнвя инстанция"
  сводятся в одну категорию — см. `analyze.py: RESULT_CANON, INSTANCE_CANON`).
- **claims_total** — сумма заявленных требований по делам, где она указана.
- **scrape_coverage / scrape_errors** — сколько дел реально удалось спарсить
  и где не удалось (с текстом ошибки — это и есть список того, что стоит
  поправить в селекторах или посмотреть руками).
- **upcoming_hearings** — ближайшие судебные заседания (из данных сайта, не
  из таблицы) — то, что реально полезно для планирования.

## Важные ограничения, учитывайте при использовании

- **kad.arbitr.ru** ограничивает частоту запросов и иногда показывает
  капчу. Скрипт не пытается её автоматически обходить — если это
  происходит стабильно, увеличьте `MIN_DELAY_SEC`/`MAX_DELAY_SEC` в
  `config.py` и/или запускайте скрапинг небольшими пачками (`--limit`),
  не всю таблицу за раз.
- Данные — публичные (картотека арбитражных дел и ГАС «Правосудие»
  открыты для просмотра без авторизации), но при массовом скрапинге
  всё равно стоит быть вежливым к серверам судов: не убирайте паузы
  между запросами и не запускайте несколько экземпляров скрипта
  параллельно на одну и ту же таблицу.
- Кэш в `data/raw/` — не удаляйте его без необходимости, повторные
  запуски `scrape` его переиспользуют (флаг `--no-cache`, если нужно
  принудительно обновить).

## Структура проекта

```
config.py             - пути, тайминги, паттерны классификации ссылок
link_classifier.py     - определение типа суда по ссылке
excel_io.py             - чтение/починка исходной таблицы
scrapers/
  base.py                - общие структуры данных, кэш, троттлинг, ретраи
  sudrf.py                - *.sudrf.ru и *.msudrf.ru (requests+BeautifulSoup)
  kad_arbitr.py           - kad.arbitr.ru (Playwright)
  mos_gorsud.py            - mos-gorsud.ru (Playwright)
scraper_runner.py       - оркестратор: маршрутизация по типу суда
analyze.py               - нормализация статусов, сводки, отчёт xlsx
main.py                   - CLI (classify / scrape / analyze / all)
data/
  raw/                     - кэш сырых ответов по каждому делу
  output/                  - итоговые xlsx
```
